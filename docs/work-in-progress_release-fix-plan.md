## 1. 本次更新目标

本次更新需要修正以下六类用户实际使用问题，并保证页面、Zustand Store、SQLite、库存流水
和重启反读结果一致：

1. 错误启用库存批次后，“删除误录记录”会卡住；同源的暂停、恢复、结束和撤销结束操作
   也可能卡住。
2. 护理液结束使用或撤销结束后页面卡住，其他品类可能同样受影响。
3. 除蛋白液启用并消耗部分库存后移动地点，实例地点改变，但批次剩余库存没有同步转移。
4. 多个品类不显示使用历史，导致暂停阶段不可查看、不可编辑。
5. 暂停使用和恢复使用后页面卡住，重启后数据库状态已经改变。
6. 批量消耗品结束后，时间轴显示数量可能增加；时间条也可能看起来多覆盖一天。

问题 1、2、5 共享同一个技术根因，应作为一个生命周期事务修正处理，不能分别打补丁。

## 2. 已确认原因

### 2.1 生命周期操作卡顿（问题 1、2、5）

原实现通过整份应用快照构造候选状态，反复执行全量 `structuredClone`、完整性检查、旧快照
恢复和新快照发布。删除有关联使用事实时，每条事实还会嵌套执行一次全量本地事务。SQLite
提交后，前端重新发布所有 Store 并重建时间轴，数据量增加后会阻塞 WebView2。

### 2.2 地点与库存未同步（问题 3）

实例地点编辑只为日抛和复用软镜转移已分配剩余量。`discrete_dose` 和
`batch_consumable` 只更新实例地点历史，没有追加相应库存转移流水。

### 2.3 使用历史缺失（问题 4）

使用历史区块被限制为只对 `rigid_long_term` 渲染。其他支持暂停、恢复的品类虽然保存了
状态区间，但页面没有查看和编辑入口。

### 2.4 批量消耗品结束后数量跳变（问题 6）

活动期间显示的是预测剩余数量；结束后改为显示库存流水重建的实际库存。预测消耗没有写入
库存事实，因此两种口径切换时数量可能回升。生命周期内部又使用左闭右开的结束边界，若
页面没有明确显示实际结束日，时间条可能看起来多一天。

### 阶段 3：实例地点与剩余库存协同转移

对应问题：3。

已确认业务口径：

- 库存页面转移由用户填写数量；
- 时间轴活动实例移动时，转移来源批次在该实例原地点的全部实际剩余量；其他地点的同批次
  库存不受影响；
- 已发生消耗的历史流水保留原地点，只移动操作日仍然存在的实际库存。

确认后执行：

- [x] 将实例地点区间更新和库存 `transfer` 流水放入同一 SQLite 增量事务。
- [x] 使用按批次、原地点实际余额计算的通用逻辑覆盖 `discrete_dose`、
  `batch_consumable` 以及软镜分配模型。
- [x] 库存不足、目标地点停用或事务失败时完整回滚。
- [x] 库存页分地点余额、实例当前地点和地点历史同步刷新。
- [x] 增加多地点、多批次、部分消耗和失败路径测试。

阶段性完整门禁 Run `fix-location-20260909` 通过：39 个前端测试文件、322 项测试、存储
架构检查、Rust fmt/clippy 和 24 项 Rust 测试均通过。

完成条件：转移不改变全局库存总量，分地点余额可由流水重建，历史消耗地点不被改写。

### 阶段 4：批量消耗品结束口径与时间轴显示

对应问题：6。

已确认业务口径：

- 结束批量消耗品时要求用户填写实际剩余数量，输入默认留空，不用预测值代填；
- 预测消耗不能直接伪造为历史库存事实；若实际剩余与账面库存不同，应通过盘点更正或丢弃
  流水调整；
- 时间轴摘要应明确区分“预计剩余”和“实际库存”。
- 实际剩余少于账面库存时追加损耗流水和损耗事实，多于时追加盘盈更正，相等时不追加；
- 撤销结束只恢复生命周期状态，已经确认的物理盘点及库存更正保留。

确认后执行：

- [x] 结束前后明确展示从“预计剩余”切换到“实际剩余/实际库存”。
- [x] 结束流程增加必填的实际剩余确认及可追溯库存更正。
- [x] 时间条使用排他结束边界计算宽度，但详情和标签显示用户选择的实际结束日。
- [x] 实现按管理模板生效，覆盖擦手纸及其他 `batch_consumable` 品类。
- [x] 增加预测不写事实、盘亏、盘盈、失败回滚、撤销结束和时间条边界测试。

阶段性完整门禁 Run `fix-batch-end-20260909` 通过：39 个前端测试文件、327 项测试，行
覆盖率 94.37%、分支覆盖率 85.41%，存储架构检查、Rust fmt/clippy 和 24 项 Rust 测试
均通过；生产前端构建通过。

完成条件：结束操作不会无说明地增加显示数量，不会自动伪造消耗事实，实际库存仍能由流水
重建。
